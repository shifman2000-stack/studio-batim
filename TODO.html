Client Portal — פורטל לקוחות

תכנון סגור · טרם החל ביצוע

מטרה

לאפשר ללקוחות להתחבר דרך כפתור ״כניסת משתמשים״ הקיים (אותו Google login של הצוות) ולהגיע לאזור לקוח ייעודי, mobile-first. המסך הראשון: קריאה וכתיבה של ״פרטי תיק״ של הפרויקט שלהם בלבד.

זהות ואבטחה

  • טבלה ייעודית חדשה client_users (נפרדת מ-profiles): עמודות id (uuid = auth.uid()), project_id (uuid FK ל-projects), email, first_name, created_at.
  • הזהות נוצרת אוטומטית בהתחברות הראשונה: אחרי ש-Google מחזיר משתמש שלא נמצא ב-profiles, פונקציית SECURITY DEFINER בשם link_client_on_login() קוראת את auth.email(), מתאימה אותו מול project_contacts, ואם נמצא — יוצרת שורת client_users עם הפרויקט הראשון התואם. מחזירה את השורה.
  • לקוח אחד = פרויקט אחד בשלב זה (אין החלפת פרויקטים).
  • מייל לא מזוהה → ניתוב שקט ל-/no-access (ללא הודעה מיוחדת).
  • RLS אמיתי על הטבלאות הזמינות ללקוח: לקוח רואה/עורך רק שורות ש-project_id שלהן תואם ל-client_users שלו.

ניתוב

  • זרימת AuthCallback: נמצא ב-profiles → צוות (ללא שינוי); אחרת — הרצת link_client_on_login → לקוח; אחרת — /no-access.
  • שומר חדש <ClientRoute> שעוטף את אזור /client.
  • /client משתמש ב-layout ייחודי mobile-first, לא ב-layout של המנהלת.

מסך ״פרטי תיק״ ללקוח (mobile-first)

כרטיסים מוערמים, גופן Heebo, רקע #F7F5F2. השדות מחולקים בין הרשאות קריאה לעריכה:

קריאה בלבד read

  • כל סקציית ״בעלי מקצוע״ (Professionals)
  • ״אחראית פרויקט״

בעלי המקצוע מגיעים מטבלת professionals המרכזית דרך FK ב-client_info — עריכה הייתה משנה את הרשומה המאסטר בכל הפרויקטים. ״אחראית פרויקט״ משותפת לקנבן — read-only מונע דליפה לתצוגה הפנימית.

עריכה edit

  • פרטי פרויקט
  • שדות רישוי
  • פרטי קשר של הלקוח

פרטי הקשר נשמרים ב-project_contacts, שבו יכולים להיות מספר אנשי קשר לפרויקט. הלקוח עורך אך ורק את שורת איש הקשר שלו, לא של בן/בת זוג.

סדר ביצוע — שכבה אחר שכבה (אימות בין כל שלב)

  1. שכבת הנתונים — טבלת client_users + פונקציית link_client_on_login. אימות: זהות נוצרת תקין, מוחזר הפרויקט הנכון.
  2. ניתוב + שומר <ClientRoute> — אימות: לקוח מגיע ל-/client; לא-לקוח ל-/no-access; צוות לא מושפע.
  3. המסך — פרטי תיק ללקוח, mobile-first, קריאה בלבד תחילה אימות: הנתונים מוצגים נכון במובייל.
  4. עריכה — הרשאות כתיבה ברמת שדה + שמירה מהמסך אימות: הלקוח עורך שדות שלו, ולא מצליח לגעת בשדות read-only.

  4. לוחצים ״צור פרויקט״.

צפוי מול בפועל

צפוי

  • נוצר פרויקט חדש עם הנתונים מהפנייה.
  • הפרויקט מופיע בלוח ה-Kanban בשלב המתאים.

בפועל

  • Production (studio-batim.vercel.app): הכפתור ״צור פרויקט״ לא עושה כלום — אין תגובה, אין שגיאה, שום דבר לא קורה.
  • Dev (localhost:5173): הפעולה נראית מצליחה (אין שגיאה), אבל הפרויקט החדש לא מופיע בלוח ה-Kanban.

הבדל Dev/Prod — חשוד מבני

ההבדל בין הסביבות מרמז על אחד מאלה:

  • פער deployment / migration — schema או RLS policy שקיימים ב-Dev ולא ב-Prod, או env-var שונה.
  • Silent failure — השורה נוצרת באיזשהו מקום אבל לא נראית ב-Kanban (אולי try/catch בולע שגיאה).
  • אי-התאמת stage_id / status / archived — הפרויקט נכנס, אבל שאילתת ה-Kanban מסננת אותו החוצה.

כיווני חקירה כשלוקחים את זה

  • ה-handler של ה-confirm במודל ״הפיכת פניה לפרויקט״ — בדקי שהוא באמת קורא ל-supabase.from('projects').insert(...). נסי לחפש try/catch שבולע error מבלי להציג למשתמש.
  • ודאי שערכי ה-stage / stage_id / archived בשורה שנוצרת תואמים את מה ששאילתת ה-Kanban מצפה לו (לדוגמה archived = false, stage_id חוקי בטבלת stages).
  • השוואת DB בין Dev ל-Prod — RLS policies על projects ועל inquiries, עמודות חדשות שאולי חסרות ב-Prod, default values.
  • ב-Prod: לפתוח Network ו-Console בדפדפן ולתפוס בקשה שנכשלת בשקט (סטטוס 4xx/5xx) או שגיאה ב-console.
  • בדקי האם converted_to_project ב-inquiries מתעדכן — אם כן, ה-flow מתחיל, אבל ה-insert נכשל. אם לא, ה-flow נחסם מוקדם יותר.

עדיפות

גבוהה. זה ה-entry path הראשי ליצירת פרויקטים חדשים. עד שזה לא יעבוד, פרויקט חדש דורש יצירה ידנית מ-Kanban — תקלה תפעולית רציפה.

FEATURE — מרחב קבצים משותף (Shared Files Workspace)

פיצ׳ר · עדיפות בינונית

מטרה

טאב / מסך חדש שבו הצוות והלקוח שניהם יכולים להעלות ולהוריד קבצים בחופשיות — נפרד מ-״מסמכים״ הקיים שמבוסס תבנית עם הרשאות per-row של hidden / view / view_edit.

המקום למשחקים שלא נכנסים למבנה: דרפטים, תמונות השראה, סקיצות, תמונות שהלקוח מצלם, הערות אד-הוק. ללא הצורך שהמנהלת תפתח גישה per-file.

היקף ראשוני

צד מנהלת

  • טאב חדש בתוך תיק הלקוח (במקביל ל״מעקב מסמכים״).
  • העלאה + הורדה + רשימת קבצים של הפרויקט הספציפי.

צד לקוח

  • פריט חדש ב-drawer (אפשר להפעיל אחד מ״כתב כמויות״ / ״חומרי גמר״ / חדש לגמרי).
  • אותו workspace, מסונן לפרויקט של הלקוח בלבד.

שדות לתצוגה לכל קובץ

  • file_name — שם הקובץ המקורי (כולל עברית)
  • uploaded_by — שם המעלה (staff מ-profiles או client מ-client_users / project_contacts)
  • uploaded_at — תאריך/שעה
  • size — גודל הקובץ

אחסון + נתיב

  • שימוש ב-bucket הקיים project-files (שמשמש את ״מעקב מסמכים״ ואת ה-portal של הלקוח).
  • תיקייה ייעודית per-project: shared/{project_id}/{uuid}.{ext} או דומה. ה-path עצמו ASCII בלבד (UUIDs) — שם הקובץ העברי נשמר רק ב-DB metadata.
  • דפוס upload + getPublicUrl ככל הנראה זהה לזה של ClientDocuments.jsx ו-DocumentsTab.jsx — שמותם מועברים ככלי.

שכבת DB

טבלה חדשה (סביר):

  • shared_files
  • — id (uuid PK)
  • — project_id (uuid FK → projects)
  • — file_url (text)
  • — file_name (text)
  • — uploaded_by (uuid → auth.uid())
  • — uploaded_at (timestamptz default now())
  • — size (bigint, bytes)

ההחלטות לגבי indices ו-constraints ייקבעו ב-implementation. DB ו-קוד תמיד נפרדים — את מטפלת ב-DDL ב-Supabase לפי הצורך.

RLS — הרשאות גישה

  • Staff (profiles.role IN ('admin', 'employee')): גישה מלאה — SELECT / INSERT / UPDATE / DELETE על כל פרויקט.
  • Client (client_users.id = auth.uid()):
    • SELECT — רק רשומות שבהן project_id = client_users.project_id
    • INSERT — רק לפרויקט שלהם, ועם uploaded_by = auth.uid()
    • DELETE — רק על רשומות עם uploaded_by = auth.uid() (uploader's-own)

החלטות שצריך לקבל ב-implementation

  • מחיקה — uploader-only? staff-only? hybrid (uploader יכול תמיד, staff override)? ההצעה הראשונית: uploader-only ל-client, staff יכול הכל.
  • הגבלת סוגי קבצים — האם להגביל ל-PDF / images / docs, או כל סוג? + הצגת preview רק לסוגים נתמכים.
  • הגבלת גודל — מקסימום per-file? (Supabase Storage default = 50MB, אפשר להעלות).
  • סדר — תצוגה chronological (חדש ביותר ראשון) או alphabetical? סינון לפי uploader?
  • התראות / badge — כשהלקוח מעלה קובץ, האם המנהלת רואה התראה במקום אחר במערכת (אדומה בטאב, badge ב-kanban, מייל)?
  • קישור מ-מעקב מסמכים — האם לאפשר ״העתק לכאן״ מהמרחב המשותף לתבנית של מסמך מובנה?

עדיפות

בינונית. המבנה הקיים של ״מעקב מסמכים״ עובד טוב לקבצים שמוגדרים מראש, אבל יש פער לתקשורת בלתי-פורמלית בין הצוות ללקוח. ההוספה הזו ממלאת אותו, ומקלה על המנהלת לא להגיב לכל בקשת שיתוף נקודתית. אפשר לבצע אחרי שהפיתוח הנוכחי של ה-portal יציב.
